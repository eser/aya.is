# Hexagonal Architecture and Public Surface

How `apps/services` separates commands from packages, logic from adapters and
modules from each other, and how settings and request metadata are shaped. The
webclient side (backend object, file layout) is in
[project-structure.md](project-structure.md).

## Commands and Packages

Scope: Where new Go code goes in `apps/services`

Rule: Each directory under `cmd/` builds one program (`serve`, `manage`,
`migrate`) and holds its entry point and wiring. Everything reusable is a
package under `pkg/`:

- `pkg/api/business/<module>`: pure business logic, one directory per module
  (`profiles`, `stories`, `privacy`, `profile_points`, ...).
- `pkg/api/adapters/<name>`: implementations of the interfaces the business
  modules declare, and the process-facing adapters (`http`, `workers`,
  `storage`, `appcontext`, and one per external service such as `github`,
  `resend`, `s3client`).
- `pkg/ajan`: framework utilities in `*fx` packages (`logfx`, `httpfx`,
  `configfx`, `connfx`, `clockfx`, `processfx`, ...).
- `pkg/lib`: small shared helpers (`cursors`, `vars`, `caching`).

File names are `snake_case` (`apps/services/AGENTS.md: Layout`). Queries live in
`etc/data/default/queries/`, migrations in `etc/data/default/migrations/`, and
the `*_gen.go` files under `pkg/api/adapters/storage/` are generated by sqlc:
change the SQL and run `make generate`, never edit them by hand
(`apps/services/AGENTS.md: SQL and generated code`).

## Hexagonal Architecture

Scope: Packages with external dependencies: storage, AI models, mail, object
storage, social providers, the HTTP layer

Rule: The business module declares the ports it needs as small Go interfaces
next to the logic that uses them (`stories.Repository` in `service.go`,
`stories.ContentTranslator` in `translate.go`, `privacy.ObjectStorage`,
`privacy.Enqueuer` and `privacy.Mailer`). Adapters implement those interfaces in
the package that owns the I/O: the PostgreSQL repository in
`pkg/api/adapters/storage`, the AI summarizer in `pkg/api/adapters/ai`. Packages
are not split into `domain/`, `ports/` or `interfaces/` directories. A
constructor takes its ports as explicit parameters; a dependency that is
optional says so in its doc comment and is nil-checked at the use site
(`privacy.NewService`: "storage and mailer are optional"). A business package
never imports `pkg/api/adapters`.

Correct:

```go
// pkg/api/business/stories/translate.go: the port beside the logic that uses it.
// Implementations live in the adapter layer.
type ContentTranslator interface {
	Translate(
		ctx context.Context,
		sourceLocale, targetLocale string,
		title, summary, content string,
	) (translatedTitle, translatedSummary, translatedContent string, err error)
}

// pkg/api/business/privacy/service.go
func NewService(
	logger *logfx.Logger,
	config *Config,
	repo Repository,
	storage ObjectStorage,
	queue Enqueuer,
	mailer Mailer,
	audit *events.AuditService,
) *Service {
	return &Service{logger: logger, config: config, repo: repo /* ... */, now: time.Now}
}
```

Incorrect:

```go
// A business module that reaches for the concrete adapter: it is tied to
// PostgreSQL and a test needs a database.
import "github.com/eser/aya.is/services/pkg/api/adapters/storage"

func NewService(repo *storage.Repository) *Service {
	return &Service{repo: repo}
}
```

**Why:** a port beside its user keeps the dependency visible in one place, lets
the adapter change without touching the logic, and lets a test pass a fake
without a database. `database/sql` types inside a business package are the same
leak in a smaller form (the TODO in `profiles/service.go` about `sql.NullTime`).

## Module Boundaries

Scope: Business modules, adapters, `pkg/ajan` and `pkg/lib`

Rule: Keep the dependency direction one way:

- **Direction.** `pkg/api/adapters/*` imports `pkg/api/business/*`; business
  modules import `pkg/ajan` (logging, clock) and `pkg/lib`, never adapters.
  `pkg/ajan` is a framework and imports nothing from `pkg/api`. Nothing in CI
  enforces this direction today (`depguard` only denies `io/ioutil`), so check
  it in review.
- **Modules.** A business module imports another one only for a shared concept
  it owns (`events` for audit and queue types, `profiles`, `users`). Do not
  create a cycle; when two modules need each other, extract the shared type or
  declare a port in the one that consumes it.
- **Data.** The repository interface of a module lists exactly what that module
  reads and writes. The `storage` adapter implements several of them; a module
  never calls sqlc-generated queries directly.
- **External services.** An AI model, mailer, bucket or provider gets its own
  narrow port in the module that needs it, so the module never learns the SDK.
  A repository interface may be wide and carries `//nolint:interfacebloat` when
  it is.
- **Errors.** Each module declares its sentinel errors (`profiles.ErrProfileNotFound`)
  and the HTTP adapter maps them to responses; the module never knows about
  HTTP status codes.

When a change needs data or behavior across modules, add or widen a port in the
consuming module, implement it in an adapter and wire it in the composition root.

## Composition Roots

Scope: `cmd/serve`, `cmd/manage`, `cmd/migrate` and `adapters/appcontext`

Rule: The command reads its settings, constructs the adapters and services in
one place and passes them in. `appcontext.AppContext.Init` is that place: it
loads the configuration, opens connections, builds the repository, adapters and
every business service with its dependencies, and `cmd/serve/main.go` hands the
services to the HTTP adapter and the worker registry. The choice between
adapters or between feature variants is a plain `if` or `switch` on
configuration in `Init`, never a registry, an `init()` side effect or a string
lookup inside a business package.

```go
// cmd/serve/main.go
appContext := appcontext.New()

err := appContext.Init(baseCtx)
if err != nil {
	panic(err)
}

// adapters/appcontext/appcontext.go
a.StoryService = stories.NewService(a.Logger, &a.Config.Stories, a.Repository, a.AuditService)
```

`init()` and package-level mutable state are flagged by `gochecknoinits` and
`gochecknoglobals` (`.golangci.yaml` enables every linter by default). The few
that exist fill a constant lookup table at startup
(`profiles/application_presets.go`, `ajan/lib/net.go`) and carry a
`//nolint:gochecknoinits` with the reason; do not add a new one for wiring.

**Why:** the wiring of a process reads top to bottom in one place, and a module
that is not constructed cannot serve a route by accident.

## Public API and CLI Surface

Scope: Exported Go APIs, settings, commands and Make targets

Rule:

- The common case works with no setting. Every setting has a default that is
  safe for production; a fixed limit a deployment may need to change is a
  setting or a named constant, never an inline number.
- Settings are struct fields with `conf:"name"` tags and `default:"value"` (and
  `required:""` where there is no safe default), loaded by
  `configfx.ConfigManager.LoadDefaults` from `config.json`, `.env` files and the
  system environment. Each module owns the `Config` struct of its own settings
  (`stories.Config`, `privacy.Config`) and `appcontext.AppConfig` composes them.
- `.env.local`, `.env.*.local` and `config.local.json` are git-ignored
  development overrides; never commit a secret
  (`apps/services/AGENTS.md: Local configuration`).
- Add a setting only for a named case; an edge case gets documentation.
- No positional boolean parameters. Use a `Config` or options struct, or a named
  type with constants.
- A new Make target gets a `## description` comment, which is what `make help`
  prints.

Correct:

```go
renderer, err := export.New(export.Options{Compact: true, IncludeDrafts: false})
```

Incorrect:

```go
renderer, err := export.New(true, false) // what are true and false?
```

## Request-Scoped Metadata Across Boundaries

Scope: HTTP handlers, middlewares, calls between packages

Rule: What identifies a request (the session of the caller, the resolved client
address) travels in the request's `context.Context` through a typed key owned
by one package: `ContextKeySessionID` of type `httpfx.ContextKey` in
`pkg/api/adapters/http/auth_middleware.go`, written by the middleware and read
by route handlers. Business inputs are parameters and dependencies come from
the composition root; neither travels in the context. A new key is a typed
constant, never a bare string, and a business service receives the values it
needs as parameters instead of reading the context for them. Logs carry IDs,
never request content (coding-practices: Structured Logging).

**Why:** a dependency hidden in a context is invisible in every signature that
needs it, and request content in logs leaves the boundary that the request
protects.
